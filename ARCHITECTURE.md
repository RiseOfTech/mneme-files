# mneme-files — Architecture

This document is authoritative for structure and mechanism. `PROJECT.md` says what the
service is for; this says how it is built. Where the two appear to disagree, `PROJECT.md`
wins on intent and this document is wrong and must be fixed.

## Shape of the service

A Clean Architecture service with one inbound adapter (REST) and one outbound adapter
(object storage). There is no database. The domain is small — a handful of value objects
and two rules (size, content type) — and that is expected: the service's value is in its
boundaries, not its logic.

```
HTTP  →  controller  →  use case  →  FileStorage (port)  →  S3 adapter  →  object storage
```

Dependencies point inwards only. The domain knows nothing of Spring, of the AWS SDK, or
of HTTP.

## Package layout

Root package: `io.github.ifamneme.mneme_files`

```
domain/            value objects, the storage port, domain exceptions
application/       use case interfaces and their implementations
adapter/web/       controllers, DTOs, exception handling
adapter/storage/   the S3 implementation of the storage port
config/            Spring configuration and @ConfigurationProperties
```

> sibling service's, so that a reader who knows one knows the other. If `mneme-core` uses
> different names or nesting, its layout wins and this section is corrected — the point is
> uniformity, not these particular words.

The domain package imports nothing outside `java.*`. This is asserted by a test, not left
to inspection.

## Domain model

All are records; none carry behaviour beyond validation.

**`FileId`** — wraps a `UUID`. Generated by `FileId.generate()` using
`UUID.randomUUID()`, which draws from `SecureRandom`.

UUIDv4 is required, and time-ordered schemes (UUIDv7, ULID) are forbidden. Reads are
unauthenticated, so the id's 122 bits of entropy are the only control protecting a file.
A time-ordered id shares a long prefix with every id minted in the same instant, which
collapses the space an attacker must search. This is a security constraint, not taste.

**`ContentType`** — wraps the permitted MIME string. The constructor rejects anything not
on the allowlist, so an invalid `ContentType` cannot exist. Types are not passed around
as raw `String`.

**`FileUpload`** — `(InputStream data, long size, ContentType contentType, String
uploader)`. What is handed to storage: the bytes of one specific upload event, plus the
token subject that made it (write-only audit metadata; see Security).

**`StoredFile`** — `(FileId id, ContentType contentType, long size, String etag,
InputStream data)`. What comes back.

`InputStream` is `java.io`, not a framework type, so it does not violate the domain's
independence.

## The storage port

Declared in `domain`, implemented in `adapter/storage`.

```java
public interface FileStorage {
    void store(FileId id, FileUpload content);
    Optional<StoredFile> load(FileId id);
    void delete(FileId id);
}
```

Three operations, permanently. No `exists`, no `list`, no `copy`, no batch variants:
nothing in this service needs them, and each one is an invitation to grow domain logic
behind the port.

**Stream ownership: the caller closes.** `load` returns a stream backed by a live HTTP
connection from the SDK's pool. An unclosed stream leaks that connection, and a few
hundred leaks stop the service. This is documented on the port and honoured at every call
site.

**`delete` is idempotent.** Deleting an absent object is not an error — S3 semantics give
this for free, and the adapter must not add an existence check to make it stricter.

**`load` returns `Optional.empty()` for a missing object**, rather than throwing. Absence
is an ordinary outcome here.

## Object storage adapter

**Client: AWS SDK v2 (`software.amazon.awssdk:s3`).** Deliberately not a vendor SDK. The
service uses four S3 operations — `PutObject`, `GetObject`, `HeadObject` is not needed
(`GetObject` returns metadata alongside the body), `DeleteObject` — all of which every
S3-compatible implementation supports identically. Coupling to a vendor client buys
nothing and costs portability.

**Backend: SeaweedFS** in development and test, chosen for an Apache-2.0 licence, a decade
of maturity, and a single-command startup (`weed server -s3`). It is a deployment choice,
not an architectural one: the port makes it replaceable by any S3-compatible service,
including managed S3/R2, by changing configuration.

**Client configuration:**

- **Path-style access must be enabled.** Against a non-AWS endpoint the default
  virtual-host style resolves `bucket.host`, which does not exist.
- Static credentials from configuration. No profile files, no credential provider chains,
  no instance metadata lookups.
- A region value is required by the SDK and is arbitrary for non-AWS backends; it is
  configuration, not meaning.

**Object key** is the id's string form. Flat: no prefixes, no directory sharding, no file
extension. Sharding solves a filesystem problem that object storage does not have; an
extension in the key would be a second source of truth about content type, competing with
the object's own metadata.

**Object metadata:**

- `Content-Type` — the *detected* type (see below), set on `PutObject`
- `x-amz-meta-uploader` — the token's `sub` claim, for audit only; nothing reads it

Nothing else. No original filename, no timestamps (the object carries `LastModified`), no
domain fields.

**Upload sizing.** `PutObject` requires the content length up front. Spring buffers the
multipart body before the controller runs, so `MultipartFile.getSize()` is exact and no
buffering of our own is needed. Multipart *upload* to S3 (the chunked protocol) is not
used: at a 5 MB cap it is never applicable.

**Error mapping.** `NoSuchKey` from `GetObject` becomes `Optional.empty()`. Other SDK
exceptions are wrapped in a domain-level storage exception at the adapter boundary — no
`SdkException` escapes into the application layer.

**The bucket is not created by the application.** It is provisioned by the environment: an
init step in compose, and test setup in integration tests. The service assumes the bucket
exists and fails fast on startup if it does not. Self-provisioning would require broad
credentials in production for a one-time concern.

## Upload path

`POST /v1/files`, multipart, authenticated. Returns `201 Created` with the file id, its
content type, and size; `Location` points at the download URL.

Order of operations, and it matters:

1. Reject on `Content-Length` above the cap before reading the body — an optimisation
   only, since the header is client-supplied and not a control.
2. The multipart parser enforces the cap while reading. This is the real gate.
3. Detect content type from the leading bytes; reject if not on the allowlist.
4. Validate size against the domain limit.
5. Generate a `FileId`, store, return.

### Size limits sit in three places

- **Multipart parser** (`spring.servlet.multipart.max-file-size` / `max-request-size`) —
  the enforcing gate, rejecting before the whole file is buffered.
- **Domain check** on `FileUpload` — where the rule is *expressed*, rather than living
  only in a YAML file. Redundant by design.
- **`server.tomcat.max-swallow-size`** — the non-obvious one. When a request is rejected
  without its body being read, the container must still consume the remainder or the
  connection is reset. If the swallow limit is below the rejected payload, the client sees
  a network error instead of the `413` the service actually sent. This must be raised
  above the largest body we intend to reject cleanly, or the error handling above is
  invisible to clients.

`MaxUploadSizeExceededException` is mapped explicitly in the exception handler; without
it, Spring's default surfaces without a `problem+json` body.

### Content type detection

The client-declared type takes no part in any decision. The stored and served type is
determined from the file's leading bytes:

| Type | Signature |
|---|---|
| JPEG | `FF D8 FF` at offset 0 |
| PNG | `89 50 4E 47 0D 0A 1A 0A` at offset 0 |
| WebP | `RIFF` at offset 0 and `WEBP` at offset 8 |

No match means rejection. **Apache Tika and equivalents are not used**: the task is to
confirm one of three permitted formats, which an allowlist answers by construction, not to
identify arbitrary ones. A general detector adds a large dependency and the possibility of
"nearly matched".

Because Spring has already buffered the upload, the stream can be read twice — once for
the signature, once for storage — with no `mark`/`reset` handling.

A mismatch between declared and detected type is not a distinct error: the declared value
is simply ignored.

## Download path

`GET /v1/files/{id}`, public, no token.

The id binds as `UUID`, so a malformed id is rejected by the framework before any code
runs. A well-formed but unknown id yields `404` as `problem+json`.

Response headers:

```
Content-Type:   from object metadata
Content-Length: from object metadata
ETag:           as returned by storage
Cache-Control:  public, max-age=31536000, immutable
```

The aggressive cache policy is *correct*, not merely convenient: content at a given id is
immutable by construction, since there is no overwrite path and every upload mints a new
id. `immutable` additionally stops browsers revalidating on reload. `public` is consistent
with reads being unauthenticated — anyone with the id may read it, so shared caches may
hold it too.

The body is returned as an `InputStreamResource`, which Spring copies and closes, so the
port's ownership rule is satisfied. The whole file is never held in memory.

**Conditional requests (`If-None-Match` → `304`) are not implemented.** Under a one-year
`immutable` policy revalidation does not occur, and supporting it would either add a
metadata round-trip per request or push an `ifNoneMatch` parameter into the port. A named
upgrade path, not a gap.

**Range requests are not implemented.** They serve video seeking and resumable downloads;
neither applies to images of a few megabytes.

## Delete path

`DELETE /v1/files/{id}`, authenticated. Always `204`, including for an unknown id.
Idempotent by design: the caller's intent is "ensure this is gone", and a `404` would
force callers to handle a case they do not care about.

## Security

The service is an OAuth2 resource server sharing `mneme-auth`'s signing key with
`mneme-core`.

**Key material.** `mneme-auth`'s **public** key only, as a mounted PEM in SPKI form
(`-----BEGIN PUBLIC KEY-----`), configured through
`spring.security.oauth2.resourceserver.jwt.public-key-location`. That property takes a
Spring `Resource`, so `classpath:` serves development and `file:` serves production
through an environment override, with no code difference. If `mneme-auth` publishes an
X.509 certificate rather than a bare public key, it is converted at packaging time — the
property does not accept a certificate.

JWKS and `issuer-uri` discovery are not used. The consequence is accepted: key rotation
requires redeploying the resource servers.

**Validation.** RS256 signature, plus `exp`/`nbf` (default) and `iss` (explicitly added).

`iss` validation is **not** on by default when the key is configured directly — Boot
derives it from `issuer-uri`, which is unused here. It therefore requires an explicit
validator layered onto the decoder, and a test proving a foreign issuer is rejected.
Without both, the requirement silently does not hold.

**`aud` is not validated in the MVP.** Tokens are currently issued to `mneme-core`, and
`mneme-core` forwards the user's token when uploading. `aud` exists to stop one resource
server replaying a token against another, which is precisely what this topology does on
purpose. With a single issuer and a single token type, and with this service accepting any
valid user by design, `aud` would add ceremony and no protection.

The intended end state is `aud` as a list containing every resource server. The transition,
when it happens, is three ordered steps:

1. `mneme-auth`: issue `aud` as an array including `mneme-files`.
2. `mneme-core`: confirm its validation accepts an array. **Check this first** — if it
   compares `aud` for equality with a string, step 1 breaks a working service.
3. `mneme-files`: enable `aud` validation.

**Endpoint security.** `POST` and `DELETE` require a valid token; `GET /v1/files/{id}` and
`/actuator/health` are open. Missing or invalid tokens yield `401`; this service issues no
`403`, since it makes no authorization decisions beyond signature validity.

**CORS is not configured.** Uploads are server-to-server and downloads are plain `<img>`
loads, neither of which involves a preflight.

```
mneme.files.storage.endpoint             S3 endpoint URL

mneme.files.storage.access-key           credentials, from environment
mneme.files.storage.secret-key
mneme.files.upload.max-size              5MB
mneme.files.upload.allowed-types         image/jpeg, image/png, image/webp
mneme.security.jwt.issuer                expected iss

spring.security.oauth2.resourceserver.jwt.public-key-location
spring.servlet.multipart.max-file-size
spring.servlet.multipart.max-request-size
server.tomcat.max-swallow-size
```

Bound as `@ConfigurationProperties` records, validated at startup. Credentials come from
the environment and are never committed.

## Errors

`application/problem+json` with a `code` property, as `mneme-core` does.

| Situation | Status | `code` |
|---|---|---|
| No/invalid token on a protected route | 401 | `unauthorized` |
| Unknown file id | 404 | `file_not_found` |
| Upload above the cap | 413 | `file_too_large` |
| Type not on the allowlist | 415 | `unsupported_content_type` |
| Malformed multipart request | 400 | `invalid_request` |

## Testing

- **Domain and use cases** — plain JUnit, no Spring context, storage port stubbed.
- **Storage adapter** — integration tests against real object storage in Testcontainers.
  Never a mock, never an in-memory S3: the value of these tests is that they exercise a
  real S3 implementation.
- **Web layer** — full-context tests covering status codes, headers, and `problem+json`
  bodies, with tokens signed by a test key pair.
- **Architecture** — a test asserting the domain package imports no framework or SDK types.

Bucket creation is test setup, not application startup.

## Rejected alternatives

Recorded so they are not re-argued.

- **A relational database.** Nothing to store: object metadata lives on the object, and
  the only plausible aggregate — per-user quotas — was declined. Rejected as unnecessary
  state.
- **`byte[]` across the port.** Simpler, and adequate at these volumes, but puts whole
  files on the heap. Streaming costs one documented ownership rule and is what a file
  service should do.
- **`Consumer<OutputStream>` inversion.** Solves ownership perfectly, at the cost of an
  awkward signature and awkward tests. Worth it for long-lived streams; not for images.
- **Vendor SDK (MinIO).** MinIO's community edition was archived in 2026. Even before
  that, the vendor client offered nothing over the S3 API for four operations.
- **Apache Tika.** Solves the general detection problem; the problem here is the specific
  one, already solved by the allowlist.
- **UUIDv7 / ULID.** Time-ordered ids leak a shared prefix, which is disqualifying when
  the id is the access control.
- **Presigned URLs.** Would remove this service from the byte path and scale better. Also
  removes the ability to enforce limits at upload, and complicates the browser's read
  path. A named upgrade path.

## Named upgrade paths

Not built, and not to be built without a decision: presigned URLs, conditional requests
(`304`), range requests, server-side image processing, per-user quotas (needs a database),
`aud` validation, key rotation via JWKS.
